# mlreg v2.0 延伸需求文件（PRD）

**文件版本：** v2.0-draft  
**撰寫日期：** 2025-07-03  
**需求來源：** Product Management / MLOps 工具使用者回饋  
**適用對象：** mlreg 開發團隊（接續 v1.0 交付成果）

---

## 背景說明

mlreg v1.0 上線後，收到多個小型 AI 團隊的使用回饋。整體而言，工具的核心功能——模型版本註冊、查詢、刪除——已滿足日常需求，輕量無雲端依賴的設計也廣受好評。

然而，隨著使用情境逐漸多元，我們觀察到幾個明顯的痛點：

1. **模型比較流程耗時**：使用者在調參實驗後，需要多次手動呼叫 `info` 逐一查看指標，再心算比較哪個版本最佳。一位使用者的原話是：「每次訓練完五六個版本，我都得把 `info` 的輸出貼到記事本裡比較，很麻煩。」

2. **輸出難以整合到腳本流程**：團隊中有人希望將 mlreg 的查詢結果接到後續的 Python 腳本或 shell 管道（例如自動部署流程），但 v1.0 的人類可讀表格格式在程式解析上相當不便。這個需求在 v1.0 的 Out of Scope 中已被預告為 v2.0 目標。

3. **資料筆數增長後效能下降**：部分使用者的專案已累積超過數千筆記錄，`list` 的回應速度明顯變慢。v1.0 設計文件中也已明確標示「10,000 筆以上效能不保證，屬 v2.0 升級觸發條件」。

4. **`delete` 操作難以恢復**：有使用者反映誤刪記錄後無從挽回，希望重要操作能有確認機制或軟刪除選項。

基於以上回饋，我們提出 v2.0 的延伸需求。v2.0 的核心原則是：**不破壞 v1.0 的 CLI 契約**，所有新功能以新增選填參數或新增指令的方式擴展。

## 需求列表

### 需求一：為 `list` 與 `info` 加入機器可讀輸出選項（修改既有模組）

**背景：** v1.0 的輸出格式為人類可讀的 Rich Table 與 Rich Panel，適合終端機互動，但無法被 shell 管道或 Python 腳本直接解析。

**需求描述：**  
在 `list` 與 `info` 兩個既有指令上，新增一個選填旗標（flag）`--output`，允許使用者指定輸出格式。v2.0 至少需支援兩種格式選項：預設的人類可讀格式（與 v1.0 行為完全相同），以及機器可讀的 JSON 格式。

當使用者指定 JSON 輸出時，程式應將結果以合法的 JSON 結構輸出至 stdout，並且**不得摻雜任何 Rich 裝飾字元、表格邊框或 emoji**，以確保下游工具可直接解析。錯誤訊息與警告訊息的輸出通道規則（stderr）維持不變，不受 `--output` 影響。

**驗收標準（使用者可觀察行為）：**
- 執行 `mlreg list --output json` 時，stdout 可被 `json.loads()` 或 `jq` 成功解析，且包含所有已登錄模型的完整資料（含 metrics 與 hyperparameters）
- 執行 `mlreg info --id <id> --output json` 時，stdout 輸出該筆記錄的所有欄位，格式為合法 JSON
- 不加 `--output` 時，`list` 與 `info` 的輸出與 v1.0 完全一致（向下相容）
- 指定 `--output` 為不支援的格式值時，stderr 應輸出明確錯誤訊息，退出碼為非零值
- `--output` 與 `--sort-by`、`--name`、`--desc` 等既有選項可自由組合，行為符合直覺

---

### 需求二：新增 `compare` 指令（全新功能）

**背景：** 使用者在多次訓練實驗後，最常見的操作是「比較兩個或多個版本的指標差異，選出最佳模型」。目前只能多次呼叫 `info` 再手動對比，效率低落。

**需求描述：**  
新增一個 `compare` 指令，接受兩個或以上的模型 ID，並以並排（side-by-side）的方式展示這些模型的指標與超參數，讓使用者一眼看出差異。

比較的呈現方式由實作者自行設計，但需滿足以下基本要求：
- 能同時展示兩筆以上的記錄
- metrics 與 hyperparameters 的 key 需對齊顯示（即使某些版本缺少特定 key，也需在對應位置留空或以明確標示呈現）
- 支援與需求一的 `--output json` 選項整合，當指定 JSON 輸出時，輸出結構需能被程式解析

此指令的 ID 清單如何傳入（例如以多次 `--id` 重複提供、以逗號分隔，或其他方式），由實作者自行決定，但需在說明文件中清楚描述。

**驗收標準（使用者可觀察行為）：**
- 執行 `compare` 並提供兩個有效 ID 時，輸出中可同時看到兩筆記錄的 project name、version、metrics 與 hyperparameters
- 當某筆記錄存在某個 metric key 而另一筆不存在時，輸出仍需完整呈現，不得因此 crash 或略去該 key
- 提供任何一個不存在的 ID 時，應輸出明確錯誤訊息並以非零退出碼結束，不得以「空白」靜默略過
- 僅提供單一 ID 時，應提示使用者至少需要兩個 ID 進行比較
- `compare` 不修改 registry.json，為純查詢操作

### 需求三：為 `delete` 加入軟刪除（soft delete）模式（修改既有模組）

**背景：** 使用者反映誤刪後無從挽回，希望有安全機制。同時，有使用者希望「隱藏」特定版本而不徹底移除，以保留歷史追溯能力。

**需求描述：**  
為 `delete` 指令新增一個選填旗標 `--soft`。當使用者加上此旗標時，不直接移除該筆記錄，而是在記錄上標記一個「已封存」狀態（archived）；未加此旗標時，維持 v1.0 的硬刪除行為不變。

被軟刪除的記錄在 `list` 的預設輸出中不顯示，但可透過新增的選填旗標（名稱與行為由實作者設計）讓使用者選擇「顯示已封存記錄」。`info` 指令應能查詢已封存記錄，並在輸出中清楚標示其封存狀態。

如何在 `registry.json` 的資料結構中表達封存狀態，由實作者自行設計，但需兼顧 `load()` 的 record 驗證邏輯，並考慮與 v1.0 schema 的相容或升級策略（例如 schema_version 是否需要更新，以及如何處理舊有不含此欄位的記錄）。

**驗收標準（使用者可觀察行為）：**
- 執行 `mlreg delete --id <id>` 不加 `--soft` 時，行為與 v1.0 完全相同（向下相容）
- 執行 `mlreg delete --id <id> --soft` 後，`mlreg list` 的預設輸出中不再出現該 ID
- 執行 `mlreg info --id <id>`（對已軟刪除記錄）時，能正常取得資料，且輸出中可辨識該記錄為封存狀態
- 使用「顯示已封存記錄」選項執行 `list` 時，已封存記錄出現在輸出中，且可與正常記錄視覺區分
- 軟刪除後再次嘗試用相同 ID 執行 `delete --soft`，應有明確的行為定義（例如：已封存則提示，或允許執行硬刪除）

---

### 需求四：將 Storage 層升級為 SQLite 後端（修改既有模組）

**背景：** v1.0 設計文件已明確預告「當資料量或查詢複雜度超過 JSON 的合理範疇時，透過 StorageBackend ABC 替換為 SQLiteBackend」。部分使用者反映記錄量增長後效能不符期待，是時候兌現這個設計承諾。

**需求描述：**  
實作 `SQLiteBackend`，讓 `Registry_Core` 可透過 v1.0 已定義的 `StorageBackend` 抽象介面，無縫切換至 SQLite 儲存。

切換機制的設計由實作者決定，可以是環境變數、CLI 旗標，或其他合理方式，但需確保：
- v1.0 的 `JsonBackend` 預設行為完整保留，現有使用者無需任何設定變更
- 當使用 `SQLiteBackend` 時，`Registry_Core` 的程式碼**不需要修改**（這是驗收的核心標準，用以驗證 StorageBackend ABC 的設計是否真的達到預期的可替換性）
- `SQLiteBackend` 需支援 v1.0 定義的所有資料不變量（ID 唯一、(project_name, version) 唯一等）

資料格式的遷移工具（從既有 `registry.json` 轉換至 SQLite）不在本次需求範疇內，但若實作者有餘力提供，列為加分項目。

**驗收標準（使用者可觀察行為）：**
- 切換至 SQLite 後端後，`register`、`list`、`info`、`delete` 四個指令的輸出行為與退出碼與 v1.0 規格一致
- 在 Registry_Core（`registry.py`）的程式碼中，不出現任何針對 `SQLiteBackend` 或 SQLite 的特判或 import
- 原有的 `JsonBackend` 測試案例全數繼續通過，不因引入 SQLiteBackend 而破壞
